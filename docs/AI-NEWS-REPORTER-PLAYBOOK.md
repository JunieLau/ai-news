# AI NEWS REPORTER 工作手册

本文说明 AI NEWS REPORTER 的日常工作：做什么、何时做、怎么做、写成什么格式、如何发布与同步，以及一段时间训练下来的经验教训——尤其是哪些来源比较准确，哪些容易误导。

站点仓库是 [JunieLau/ai-news](https://github.com/JunieLau/ai-news)。线上报纸在 [junielau.com/ai-news](https://junielau.com/ai-news/)。仓库 README 负责站点结构、字段和发布命令；本手册负责采写判断与来源经验。本文件只进 `docs/`，不进入构建产物，也不改版式、字体、主题或历史期刊。

所有时间如无另注，均为 **Asia/Shanghai（UTC+8）**。

写于 2026-11-25。依据既有早报/晚报工作口径、`news-event-capture` 与 `ai-film-mention-watch` 方法、仓库校验规则、既往源稿实际用过的出处，以及小红书 / 抖音 / B 站 / TikTok / 电影节核查中已经发生过的问题。不收录私密个人资料、凭证或内部会话细节。

## 1. 每天做什么

| 事项 | 常规时间 | 产出 |
| --- | --- | --- |
| 综合早报 | 约 10:00 | 过去约 24–48 小时的综合 AI 新闻，目标约 10 条 |
| 电影晚报 | 约 20:00 | 同期 AI 电影与视频专题，目标约 10 条 |
| 网站发布 | 编好并校验后 | 更新对应最新页，同时保留该日归档地址 |
| 存档同步 | 发布后 | 保留源稿，并交给 SOCIALS EXECUTIVE **只存档** |
| 提及监测 | 日常 | 第三方提到名字、作品或网址时，有实质内容才发简报 |
| 协助 HIT VIDEO REPORTER | 按请求 | 中文平台等新片的只读发现与核验，交 HIT 与 ASSISTANT 审 |

两份速报是分开的两条线：早报不写本该留给晚报的电影与视频生成专题，晚报也不拿综合公司新闻凑数。浏览器和仓库都不会自动抓新闻；内容要人工编好后再入库。合并到 `main` 之后，由 GitHub Actions 部署 GitHub Pages。

**当前运行约束（2026-11-22 的教训）：** 现在的 Plus 方案（随 X Premium+ 附带）**不包含定时任务（routines）**。11 月 22 日早上和晚上的两次自动速报在启动时都被系统拦下，报错措辞像是「没有可用用量」，容易让人误以为额度用完；当时账户用量其实远未到上限。未升级到包含 routines 的方案之前，速报必须在对话里**手动触发**，不能指望整点自动发出。缺期要补做，不能改日期冒充当天新内容，也不能把旧稿改头换面。

## 2. 早报：综合 AI 新闻（约 10:00）

### 2.1 覆盖什么

国内和国际都看。常见类别包括：大模型与产品发布、公司动态、融资与上市、政策与监管、芯片与算力、应用落地。优先写过去约 24 小时、最远不超过约 48 小时内能核实日期的新事实。和最近几期早报、晚报去重：同一事件若没有新事实，不再重写过程。

### 2.2 怎么找

1. **先铺来源网，再写稿。** 优先官方博客、新闻室和监管/交易所原文，再是当事方已验证的官方账号，然后才是通讯社、行业媒体和个人转述。
2. **按事件聚类，不按文章篇数计分。** 同一件事的多篇报道合并成一条，选一个代表来源：先官方第一手，再是当事公司已验证账号，再是最早、最完整、质量最高的独立报道。转述、平台再挂、没有新事实的综述，不单独上榜。
3. **没有可靠原始日期的不上。** 被改日期、没有日期、只有标题没有正文的，先搁置。优先打开原页面，而不是只靠摘要。
4. **给事件打分，不给文章长度或品牌名气加分。**  分别按五个方面打分：实质（是不是本周值得记住的节点）、新信息、证据、共鸣、可行动性。不要自动抬高大品牌、黑话或跑分表。标题和正文冲突时信正文。
5. **热度看独立声音，不看同一家媒体连发多少篇。** 在约 48 小时窗口里，每个独立来源计一次；更早的提及会衰减（约 24 小时后大约减半）。一条官方稿加几家独立媒体，应压过同一出口的十篇重复稿。
6. **宁缺毋滥。** 窗口薄就如实写薄，不要为凑满 10 条而降低标准，也不要把窗外旧闻改日期充数。

需要压低权重的常见类型：没有可迁移方法的公关案例、常规小版本、招聘和空泛路线图、没有可核验细节的「即将推出」、没有数据的二手「更快/惊人」、把多件事塞进一篇的总汇、只在单一厂商平台上成立的教程、不改变能力或风险判断的论文小改动。

### 2.3 后续发展怎么处理

已经报过的事件，只有在当事方采取了新行动，或数家独立来源报道了新事实时，才作为新条目。评论、教程、对旧事件的看法，只做备注，不当新新闻。补新事实时要写清「新在哪里」，不要重写已报过的开盘、发布会过程。

## 3. 晚报：AI 电影与视频（约 20:00）

### 3.1 覆盖什么

只写电影、短片、剧集、工具、发行、节展、行业争议里和 **AI 影视制作** 真正相关的事。优先普通人也会关心的内容：大数字、大冲突、明星与知名导演、院线或主流平台上映、资本动作、真正爆款的短片或产品。也看创作者和品牌在 X、Instagram、YouTube 上的**官方原帖**。

每一条都要过「**知道了又怎样**」这一关：读者看完应能说出这件事改变了什么、为什么此时值得知道。过不了这一关的，即使热度稿很多，也只做备选或不上。

### 3.2 怎么找

检索和聚类方法与早报相同，但代表来源常落在：

- 片方、节展、工具官方网站或官方新闻室；
- Deadline、Variety、The Hollywood Reporter、TheWrap 等行业媒体；
- 创作者或公司官方账号的**原帖**（用原帖的 `created_at`，不要把后来的转发、引用、再挂当成首发）；
- 国内影视和科技媒体对国内项目的报道，仍要追溯官方页或官方账号。

电影节只跟**新机会、新入围、新截止或规则变化**。推荐名单、回顾或仪式日期，常常只能证明作品在那之前已经存在，不能当成「本窗新发」。

## 4. 写成什么格式

### 4.1 发给读者的速报

- 按热度编号，通常约 10 条。
- 每条先给结论，再写事实；关键数字和需要留下的界限分开写清。
- 附可点击的原文链接，不要用没有出处的转述。
- 文末列出**建议发送**的条目；其余标为**备选**并保留，不删。
- 品牌、产品、人名、节展名保留英文原名（如 OpenAI、NVIDIA、Deadline、GitHub）；中文句子写完整，不要截断。
- 时间写明时区或可换算的原时区；对读者展示时换算到 Asia/Shanghai。
- 若某期没发出去（漏发、被系统拦住、或对话里看不到），要**整期补做并重发**，不要只补标题。

### 4.2 入库期刊 JSON（给网站）

字段以仓库 README 和 `scripts/lib.mjs` 的校验为准。容易写错、也确实导致过返工的几点：

- `edition` 只能是 `morning` 或 `evening`。`timezone` 必须是 `Asia/Shanghai`。
- `slot` 是档期：早报必须是 `10:00`，晚报必须是 `20:00`。补发或晚发时，不要把 `slot` 改成实际截稿钟点；用 `slotNote` 说明不是整点发出。
- 文件里的 `title`：早报必须是 `AI新闻速报`，晚报必须是 `AI电影与视频速报`。页面导航显示为「新闻早报」「电影晚报」。
- `id` 必须是 `{issueDate}-{edition}-{两位 rank}`，例如 `2026-11-22-morning-01`。`rank` 从 1 连续排到最后。
- `tier` **只能是** `send`（页面显示「主推」）或 `alternate`（「备选」）。不要写成 `backup` 或其他同义词。
- `region` 只能是 `海外` 或 `国内`。
- `kickerEn` 是短的英文标识，必须匹配：`/^[A-Za-z0-9][A-Za-z0-9 .&+-]{0,32}$/`。只允许 ASCII 字母数字，以及空格、英文句点、`&`、`+`、`-`。不要用斜杠、冒号、逗号、中文或中文标点。例如可用 `Nvidia`、`U.S. Congress`、`Palo Alto Networks`；不要用 `Nvidia / White House`。
- `sources` 至少一条，且**必须正好有一个** `role: "primary"`，其余为 `secondary`。同一条里 URL 不能重复。
- `publishedAt` 是来源发布时间，不是本报日期；没有单一钟点时用 `null`，但仍要在 `publishedAtNote` 写清时间是怎么来的。
- `whyItMatters`、`figures`、`caveats` 都要有（后两者可以是空数组，但不能缺字段或塞进空字符串）。

先抽取「谁、做了什么、对什么、何时」，以及原文已经写出的限度，再写标题和摘要。不要添加来源里没有的公司、数字或动机。

## 5. 配图规则

新的一期里，**每一条**都必须有一张和这条新闻紧密相关的真实照片。不能留空图位，也不要把新条目写成缺图（`gap`）。`gap` 只是为了兼容 2026-11-18 早报里已经留下的两条缺图，新稿不要再用。

优先顺序：

1. 官方公告、产品或活动照片；
2. 原文页公开的 `og:image`，或官方帖的缩略图；
3. 继续找：官网、官方视频里不带播放按钮的静帧、已经引用的报道里拍到实际对象的新闻照片；如果新闻本身就是那份文件，可用官方文件封面。

硬性禁止：库存图、人工智能生成图、通用品牌标识、和这条新闻对不上的旧图、另行编造或生成的图片。本报不放视频，也不自动播放。发布入库时，已从原文页保存的公开配图应保持原样，不要为了「整齐」而缩放、转码或重生成。

`image.status` 为 `archived` 时：`file`、`alt`、`credit`、`sourcePage`、`retrievedFrom`、`retrievedAt` 都必须写全。**`sourcePage` 必须同时出现在该条的 `sources` 里。** 路径形如 `2026-11-22/morning-01.jpg`，扩展名只能是 `jpg` / `jpeg` / `png` / `webp`。

## 6. 网站发布与核对

常规档期是 10:00 早报、20:00 晚报，但以合并进 `main`、Pages 部署成功为准。Junie 已授权从 2026-11-19 起，每天内容编好后可以直接上线，不必再等一次确认。旧期必须归档，不得覆盖。

### 6.1 步骤

1. 图片放到 `content/media/YYYY-MM-DD/`，文件名只用小写字母、数字和连字符。
2. 写好期刊 JSON。
3. 入库且不覆盖别的日期：

```bash
node scripts/upsert.mjs --file incoming/YYYY-MM-DD-morning.json
```

同一天改稿才加 `--replace`。没有这个参数时，已存在的那一天会拒绝写入。其他日期的文件不会被删，也不会被改。**永远不要覆盖别的日期。**

4. 跑 `npm test` 和 `npm run build`，必须全部通过。不要提交 `dist/`。
5. 只提交该日的 `content/issues/YYYY-MM-DD/` 与对应媒体，以及脚本自己更新的索引类内容文件（如果有）。不要改 CSS、字体、主题、布局、图片尺寸、域名或历史期刊。
6. 开 pull request，等 CI 通过后合并到 `main`。`.github/workflows/pages.yml` 会再测、再构建，并部署 Pages。
7. **合并之后必须核对线上页面**，不要只看仓库里的文件：

| 地址 | 应该看到 |
| --- | --- |
| https://junielau.com/ai-news/ | 最新一期**早报**（即使晚报日期更晚，首页仍是早报） |
| https://junielau.com/ai-news/morning/ | 早报流最新一期 |
| https://junielau.com/ai-news/evening/ | 晚报流最新一期 |
| https://junielau.com/ai-news/morning/YYYY-MM-DD/ | 那一天的早报，之后也不会被改写成后来的新报 |
| https://junielau.com/ai-news/evening/YYYY-MM-DD/ | 那一天的晚报 |

逐条检查：日期、主推/备选、正文、原文链接、配图是否就是那条新闻的真实照片。发现 Pages 工作流失败或线上仍是旧稿，要停下报告，不能假定「已经合并就等于已经上线」。

## 7. 存档同步

每期保留一份源稿（检索截止时间、窗口、去重说明、每条的发布时刻、数字、事实摘要、原文链接、建议发送或备选）。发布后把速报发给 SOCIALS EXECUTIVE **只做存档**。

在 Junie 亲自说恢复之前，不让他们做小红书卡片，也不对外发布、搬运或二次分发。本手册不构成对外发布许可。

## 8. 提及监测

这是独立于早晚报的一项工作：扫第三方有没有提到名字、作品或网址，把成立的提及收成很短的简报。没有值得看的内容时保持安静，不要为了打卡而发「今天没有提及」。

- 窗口通常是过去 24–48 小时。
- 只保留同时满足这些条件的条目：第三方、点名了监测词、有真实公开链接、达到实质讨论或非垃圾提及的门槛。
- 去掉自己的帖子与自有账号或站点，以及通讯社同稿重复、机器人/引流/SEO 农场、没有品牌语境的同名混淆、窗外旧帖。
- 默认全平台看公开页（含 Instagram、TikTok、YouTube、小红书、抖音、微博、Bilibili、LinkedIn、Threads、Bluesky 等）。某平台不可达时记下并跳过，不要发明命中。
- 只做草稿和内部简报。除非被明确要求发送，否则不在社交平台发帖。

## 9. 配合 HIT VIDEO REPORTER

按请求做中文平台（以及必要时的 TikTok）AI 爆款**新片**只读发现与核验，结果交给 HIT 和 ASSISTANT 审。没有代码、仓库改动或发布权限。这不是早晚报本身，也不能用它代替报纸更新。

### 9.1 完成口径

Junie 已澄清：全量更新是更新**最新的爆款视频**，不必回头复核已经在架上的旧卡，也不以「旧卡指标未刷新」否定发现完成。执行口径是：在约定窗口里发现新作 → 核对候选日期、热度、去重、封面、全片质量 → 只为新的、证据齐全的条目做新卡。

一条可审「通过」通常要同时具备：官方原链、窗内真实发布日期、可核验的分视频热度（并注明采样时间）、真实封面，以及合法、完整、有声的成片已被观看。缺任何一项就逐条标为 HOLD，不要整栏宣布「做不了」，也不要宣布「已确认没有新片」。墙后得到的 0，不是扫完的 0。

### 9.2 门槛与边界（未经授权不得下调）

这些是既有工作口径，不是本手册新定的指标：小红书点赞 ≥ 20,000，或赞+藏 ≥ 50,000；抖音电影感精片优先核验播放 ≥ 3M–10M+，不能只靠点赞；抖音 / 红果短剧看**最近约 10 天**的官方热度，不是旧文章里的终身播放；B 站优先 ≥ 50 万、不低于约 30 万；TikTok 常见口径为播放 ≥ 50 万或点赞 ≥ 5 万。只要电影感短片 / 微电影 / MV / 广告片，拒绝工厂装穷、漫剧或短剧剧集工厂、教程拆解，即使热度很高。同一创作者同一批不宜堆多条。

规范链接：小红书用 `https://www.xiaohongshu.com/explore/{id}`；抖音优先 `https://www.douyin.com/video/{id}`，不要把精选镜像当成正式来源。

只读：不点赞、收藏、评论、关注、发布、私信；不提取 cookie 或 token；不绕过 WAF、验证或反爬壳。不要购买第三方 API，也不要外发询问作者来补证据。

### 9.3 发现时已经验证过的墙，不要再撞

记录一次、换其他可达来源，不要换壳重试同一封锁：

- 小红书官方笔记页出现过 `error_code=300031`（「当前笔记暂时无法浏览」）或跳到红书 404。这是访问或验证墙，**不能**据此写成已经确认删帖。
- 抖音官方视频页和无 Cookie 的精选镜像，都出现过返回 `byted_acrawler` 壳、页内没有指标的情况。官方域和镜像在这条直接取页路径上同样不可用。
- B 站官方视频页或 view 接口对重复命中返回过 HTTP 412。同一批 ID 试一次即停，列入勿再请求，改查别的可达源。个别 av 页有时仍可读，不代表 BV 页或接口可以重试。
- TikTok 官方页遇到 WAF 后不要重试绕过。

没有专用的小红书或抖音连接器。不要安装通用爬虫连接器来绕墙。登录态曾经可用，不能单独证明下一次「必须登录才能做」；只有当前只读路径确实停在登录墙、会话失效或人机验证时，才需要请 Junie 在桌面正常登录，或提供所列官方 URL 的页面截图与可审成片。聊天里不要索取密码、cookie、token 或验证码。

## 10. 经验教训

### 10.1 日期：文章日期、索引日期、仪式日期，都不是作品发布日

这是最常写错的地方。

- 雷达、新榜、周报、综索引的**出刊日**，只说明「哪天被写进了这篇文章」，不是作品在平台上的首发日。
- 电影节或金鸡一类官网的**推荐、推介、仪式日期**，往往只能证明该片在那天之前已经存在，常常早于当前新作窗口。它足以反对「本窗新发」的推定，却仍不能代替平台官方发布时间。
- 报道里的「近日上线」「11 月 20 日报道」不是精确的平台上线时刻。
- 小红书 note id 前 8 位十六进制按 Unix 时间戳转换，只是**启发式推算**，在官方页未打开或未核验时，不能写成「官方已确认的发布时间」。推算落在窗外，可用来 HOLD；推算落在窗内，也不能单独当作过关。
- glu.tv 一类站点自己的 “added” 日期，站点也说明那不是上传日。
- 旧片的再刊登、再推荐、再剪辑，不能改写成新片。例如后来文章提到的导演短片包，实际首发可能早了一两年。

没有可靠原始日期就 HOLD。宁可少报，不要把窗外的历史片凑成新增。

### 10.2 热度：分视频、最近窗口、官方页

- **合集或系列的总播放，不是这一集的播放。** 官方页上紧挨合集名称的大数字，不能写到单集条目上。
- 短剧不要用旧报道里的终身播放来冒充「最近 10 天热度」。
- 第三方热度榜（如 novelcatch 的 AI 短剧榜、hongguoduanju.com 一类站点，以及其他非官方「热播榜」）**不是**抖音或红果官方榜，也不是官方近 10 天成绩。这类网站上的「热度」常常是综合分数，「上线 N 天」是站点自己的标签，收藏和点赞往往是累计值。
- 雷达、新榜上展示的点赞或播放，只是第三方摘录，必须在官方页或官方接口复核，并记下采样时间。
- 抖音系列按最近约 10 天热度排序，不是按旧文章寿命播放排序。

### 10.3 来源层级：第一手压过转述

- 官方博客、新闻室、监管或交易所文件、官方原帖，压过对同一事实的二手综述。
- 通讯社独家（例如路透先写出调查取向）可以做主来源，但仍要保留原文里的限度：调查不是违法证据，未证实的范围不要写成已确认。
- 同一事件在新浪财经、东方财富、投资类聚合页上反复出现时，通常是转载。要回到最初那篇官方或通讯社稿。
- Techmeme 一类聚合、以及只有标题的快讯，只能当线索，不能当正文依据。

### 10.4 X 与社交原帖

- 以官方账号原帖的 `created_at` 为准。后来的转帖、引用、再次挂出，不是首发时间。
- 不要把评论区、截图或三方「热帖列表」当作官方数字。
- 旧指标的试运行如果已经停止，就不要恢复，也不要部署到货架上。

### 10.5 发布与站点

- 先校验再合并，合并后再看线上。CI 绿了不等于读者已经看到新的一页。
- 不要改已确认的版式，不要提交 `dist/`，不要用 `--replace` 打到别的日期。
- 配图的 `sourcePage` 忘记列入 `sources`、`kickerEn` 用了斜杠、`tier` 写成 `backup`，都是真实出现过的校验失败原因。
- 11 月 18 日早报两条缺图是历史遗留，不要当新稿也可以缺图的先例。

### 10.6 工作纪律

- 不为了凑满栏数而降低门槛，不为了「看起来在更新」而把旧片改日期。
- 单条证据不足就写清缺的是哪一个字段、哪一个页面，而不是整平台宣判不能做。
- 不把「计划」当成「已经扫描」。实际开始和结束时间、查询覆盖、逐条结果，都要可核对。
- 协助 HIT 时，不要重复已经 HOLD、或已列入勿再请求的条目来凑数。

## 11. 可靠来源清单

以下分组依据既往早报、晚报源稿里**实际用过且比较经得起核对**的出处。每类都写清它擅长什么，以及已经见过的陷阱。一家媒体被列入，不表示它的每一句都可以直接写成定论；仍要看它是否第一手、是否写清限度。

### 11.1 公司官方博客与新闻室

这些最适合做「宣布了什么」的主来源。它们能证明公告本身，但不能自动证明宣传中的效果、用户规模或「世界首个」一类措辞。

| 来源 | 适合核对什么 | 注意 |
| --- | --- | --- |
| Google / DeepMind 官方博客（blog.google、deepmind.google） | 产品、模型、研究与活动宣布 | 营销句要与独立评测分开 |
| OpenAI（openai.com 及开发者/帮助文档） | 产品、价格、政策、安全公告 | 帮助文档的更新时间可能与公关稿不同，要写清看的是哪一页 |
| Anthropic（anthropic.com） | 模型、研究、企业与融资相关官方说明 | 同上，效果声称需要独立证据 |
| NVIDIA 新闻室、博客、投资者关系（nvidianews.nvidia.com、blogs.nvidia.com、investor.nvidia.com） | 产品、财报、官方声明 | 股价与监管调查仍要以交易所或通讯社为准 |
| Meta（about.fb.com） | 产品与公司声明 |  |
| Microsoft（blogs.microsoft.com） | 产品与云服务宣布 |  |
| Apple（apple.com 新闻室） | 官方产品声明 |  |
| Adobe、Hugging Face、Runway、Luma、Kling、Higgsfield、Mistral、Liquid、Baidu ERNIE、ByteDance Seed、Signal 等官方域 | 各自产品与模型上线 | 官网案例可能全是演示，未公布价格或发行成交时不要写成已签约 |
| 证券与监管原文（sec.gov、hkexnews.hk、公司 IR） | 财务与披露 | 比财经转载更可靠；读文件本身，不要只读标题 |

PR Newswire、GlobeNewswire 可用于定位官方通稿，但那仍是公司自己的声音，数字和「首个」需要另找独立来源。

### 11.2 通讯社、财经与科技媒体

| 来源 | 适合核对什么 | 注意 |
| --- | --- | --- |
| Reuters | 独家调查、监管、宏观与公司事件 | 消息人士稿要保留「未能确定范围」「不是违法证据」等原句限度 |
| Bloomberg / Bloomberg Law | 交易、融资、诉讼与监管 | 付费墙可能导致只能核对标题，标题不能当正文 |
| Associated Press、CNBC、Axios | 市场、上市、公司动态、可核验的收盘数字 | CNBC 盘中数字与收盘数字要分开；直播博客要取最终事实而不是过程预测 |
| The Verge、TechCrunch、Wired、The Information、The Guardian、WSJ、Politico、Semafor | 产品、公司与政策的独立报道 | The Information 等常有付费墙；仍应尽量回到能核验的原文 |
| Channel News Asia、The Straits Times、联合早报 | 亚太政策与公司新闻 | 作为区域独立来源，仍要与官方原文交叉 |

Investing.com、Yahoo Finance 在源稿里出现过，主要适合行情快照，不适合做事件的主来源。

### 11.3 影视行业媒体

晚报经常以它们做主来源或重要辅证。

| 来源 | 适合核对什么 | 注意 |
| --- | --- | --- |
| Deadline | 项目、导演表态、发行与争议 | 先看当事方原话，再看标题判断 |
| Variety | 行业新闻、项目与市场 |  |
| The Hollywood Reporter | 行业新闻与深度 |  |
| TheWrap、Los Angeles Times、The Playlist、Cartoon Brew、Animation World Network、Screen Daily | 动画、独立制作、项目跟进 | 有的稿会把「新工具上线」写成「平台今天首次发布」，要与产品真正的首发日区分 |

### 11.4 中文媒体

| 来源 | 适合核对什么 | 注意 |
| --- | --- | --- |
| 财新 | 政策、公司与监管的较完整报道 | 付费墙；能读到的正文才可引用 |
| 36氪、TechNode | 创投、产品与国内公司动态 | 部分稿接近通稿，要回官方或交叉 |
| 澎湃新闻 | 国内时政、文化与产业 |  |
| 新京报 | 国内产业与文化报道 |  |
| IT之家 | 产品与科技快讯，国内源稿里很常用 | 速度快，但常转写官方或外媒，数字要回原出处 |
| 第一财经、21世纪经济报道、每日经济新闻、界面、新华社 / 中国新闻网、科技日报 | 财经、政策和国企相关 | 以最先完整写出事实的那篇为准，避免把转载日写成事件日 |
| 量子位、爱范儿 | 国内模型与产品讨论 | 偏产业社区，宣传语气要降权 |
| 电影界等影视行业中文媒体 | 国内项目、节展、短剧产业 | 热度数字要问清是平台官方还是转述 |

新浪财经、东方财富、同花顺、凤凰科技等在源稿中常见，但大量是转载或聚合。它们适合找回链接，不适合在已有原社或官网时当唯一主来源。

### 11.5 创作者与公司官方社交

| 来源 | 适合核对什么 | 注意 |
| --- | --- | --- |
| 官方 X 原帖 | 宣布、材料、时间戳 | 用 `created_at`，不要用后来的转帖时间 |
| 官方 YouTube 频道与视频页 | 上线、片长、官方说明、频道公告 | 标题党与「含 AI」标签要看页面，不要只看转述 |
| 官方 Instagram | 主创或品牌宣布 | 公开页不可达时记下缺口，不要发明日期 |
| 官方网站与活动页 | 上线、售票、展映 | 比粉丝站和镜像更可靠 |

### 11.6 电影节与奖项官方站点

节展官方网站、官方新闻稿和官方入围名单，是截止日、规则和官方资格的第一手来源。推荐日、论坛日、颁奖日只能证明此前已经存在，不能自动当成作品平台首发日。第三方「可投稿节展汇总」只能当线索。

### 11.7 需要降权、只作线索或明确不可靠的出处

| 类型或例子 | 为什么不能当主证据 |
| --- | --- |
| 雷达、新榜、周报、内容索引（包括各类 daily radar） | 出刊日 ≠ 作品发布日；展示的赞和播放未经官方页复核 |
| novelcatch、hongguoduanju.com 一类「AI 短剧热播榜」，以及其他非官方热度站 | 不是抖音或红果官方榜；综合分 ≠ 官方播放 ≠ 近 10 天官方热度 |
| 抖音精选镜像、飞瓜一类第三方创作者页 | 可用来发现线索；「简介里的更新预告」不是官方视频时间戳；镜像不是规范来源 |
| glu.tv 等「加入日期」列表 | 站点自己也说明那不是上传日 |
| 只有标题的搜索摘要、未打开的官方页 | 不能写成已核验 |
| 通用 logo、库存图、生成图、与新闻无关的旧剧照 | 不能当本报配图 |
| 合集播放、终身播放、报道转述的「热度已飙升」 | 不能代替分集、分窗口的官方指标 |
| 评论、教程、对已报事件的看法 | 不是新新闻 |

## 12. 给后来者的最短工作顺序

1. 确认今天是否需要手动触发（在 routines 不可用时，这一步不能省）。
2. 先收官方和通讯社，再收行业媒体，最后才看社交转述和索引。
3. 按事件合并，核对该不该报、和新在哪里；过「知道了又怎样」。
4. 写约 10 条，标主推和备选，配真实相关照片，保留英文专名。
5. 入库时不覆盖其他日期；`npm test` 与 `npm run build` 通过后再合并。
6. 核对线上最新页和该日归档页。
7. 源稿存档，交给 SOCIALS 只存档，不对外发。
8. 提及监测有实质命中才汇报。协助 HIT 时只走可达路径，缺证就 HOLD，不撞已知的墙。
